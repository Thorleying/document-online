# ADR-0003：浏览量走异步上报 + Redis 计数 + 定时回写，不在渲染请求内写库

- 状态：Accepted
- 决策时间：2026-08-25 17:34:55 +08:00
- 负责人：项目所有者
- 关联 Spec/Ticket：`docs/specs/0001-online-document-sharing.md`
- 替代/被替代 ADR：无

## 背景

浏览量是本产品唯一需要的互动数据，也是全系统唯一的高频写入路径。阅读页是被外部链接直接打开的入口，其首屏耗时直接决定读者是否留下。

朴素实现是在阅读页的渲染请求里执行 `UPDATE documents SET view_count = view_count + 1 WHERE id = ?`。这个写法有两个具体问题：

1. **热点行锁**：所有访问同一文档的请求都要竞争同一行的写锁。文档越受欢迎，锁竞争越严重，而受欢迎恰恰是分享成功的标志——系统会在最需要表现好的时候表现最差。
2. **阻塞首屏**：写事务串在渲染路径上，数据库的任何抖动都会直接转化为读者看到的白屏时间。而这次写入对读者本人毫无价值。

此外还需要区分 PV 与 UV，并按天、按分享渠道聚合，明细数据量会随时间线性增长。

## 决策

把计数从渲染路径上彻底摘除，拆成四段：

1. **上报**：阅读页渲染完成后，前端异步 `POST /api/view`，携带文档 ID、分享链接 ID（永久链接则为空）和访客 ID。上报失败静默处理，绝不影响阅读。
2. **计数**：服务端在 Redis 上执行 `INCR`，同时写一条 `view_logs` 明细。
3. **回写**：定时任务每分钟把 Redis 计数批量刷回 `documents.view_count`。
4. **聚合**：定时任务把明细聚合进 `doc_daily_stats`，所有图表只查这张预聚合表。

配套规则：

- **UV 去重**：访客身份用 `localStorage` 中的匿名 UUID，配合 `hash(IP + UA)` 兜底（用户清缓存或禁用存储时仍能大致去重）。同一访客对同一文档在 30 分钟窗口内只计一次 UV。
- **防刷**：同一 IP 对同一文档 1 分钟内多次上报只计一次；过滤已知爬虫 UA；上报接口做限流。
- **一致性**：页面展示以 `documents.view_count` 为准，允许最多一分钟延迟。阅读场景下没有人会盯着计数器看它是否实时。
- **数据保留**：`view_logs` 含 IP 与 UA，属于个人信息，保留 90 天后由定时任务清理；`doc_daily_stats` 不含个人标识，永久保留。
- **渠道归属**：永久链接的访问在 `view_logs` 中记为 `share_link_id = NULL`；但 `doc_daily_stats` 用 `(document_id, share_link_id, stat_date)` 作主键而 MySQL 主键不允许 NULL，故该表用 `0` 表示永久链接，转换由聚合任务负责。

## 备选方案

1. **渲染请求内同步 `UPDATE`**：最简单，无额外组件。
2. **渲染请求内同步写，但只写明细表**：避免热点行锁（明细是 append-only），展示时实时 `COUNT`。
3. **应用内存缓冲 + 定时 flush**：不引入 Redis，在 Node 进程内累加，定时批量落库。
4. **接入第三方统计（如 Umami、Plausible）**：不自己实现。

## 选择理由

方案 1 的两个问题在背景里已经说明，且它们会在系统最成功的时候爆发，不可接受。

方案 2 消除了行锁，但把成本转移到了读侧：展示浏览量需要在明细表上 `COUNT`，而明细表会增长到百万行级，每次阅读页渲染都要扫一遍是更糟的交易。

方案 3 是本决策在无 Redis 时的退化形态，取舍已知：多实例部署会丢计数（各进程独立缓冲），进程重启会丢未 flush 的增量。因为项目本来就要用 Redis 做限流和分享链接密码会话，额外把计数放上去的边际成本接近零，所以不采用退化方案。这一点在 ADR-0001 中也有记录。

方案 4 能省下全部实现工作，但本产品的统计需求与分享链接强绑定——需要知道"发给 A 公司的那条链接被打开了几次"，这是第三方通用统计工具无法表达的维度。而且访问数据涉及客户信息，托管到第三方不合适。

选择异步上报还有一个副作用是正面的：它天然过滤掉了大部分不执行 JavaScript 的爬虫，使 PV 更接近真人访问量。代价是禁用 JavaScript 的真人访问不会被统计，这个偏差在阅读类产品上可以接受。

## 影响与风险

- 正面影响：阅读页首屏不受计数写入影响；热门文档不产生行锁竞争；统计维度完整（PV/UV/按天/按渠道）；图表查询复杂度与文档年龄无关。
- 负面影响：引入最终一致性，计数最多延迟一分钟；引入两个定时任务，需要监控其存活；`view_logs` 与 `doc_daily_stats` 对"永久链接"的表示不一致（NULL 与 0），这是 MySQL 主键约束导致的妥协，必须在聚合任务里显式转换，是一处容易出错的地方。
- 安全与隐私影响：`view_logs` 存储 IP 与 UA，属于个人信息，须遵守 90 天保留期。上报接口对匿名访客开放，是系统唯一的公开写入口，必须限流。
- 性能影响：Redis `INCR` 为 O(1)；明细写入为顺序 append；回写与聚合为批量操作。
- 运维影响：新增 Redis 依赖；定时任务失败会导致计数停滞（但不丢数据，明细仍在写），需要告警。

## 迁移与回滚

首次实现，无迁移。若 Redis 不可用，可临时降级为方案 3（应用内存缓冲），`documents.view_count` 的语义不变，仅精度下降。`view_logs` 明细始终直接落库，因此即使计数链路完全失效，也能从明细重建计数。

## 验证方式

- 单元测试覆盖：UV 30 分钟窗口去重、同 IP 1 分钟防刷、爬虫 UA 过滤、永久链接的 `NULL` 到 `0` 转换。
- 集成验证：上报接口在 Redis 不可用时不抛错到阅读页，且明细仍然落库。
- 手工验证：连续刷新阅读页，确认 PV 增长而 UV 不变；一分钟后确认 `documents.view_count` 与 Redis 计数一致。
- 回归验证：从 `view_logs` 重算某文档的 PV，与 `documents.view_count` 比对，差值应在一个回写周期内。

## 后续事项

- 定时任务需要存活监控与失败告警，本期不实现，第四期补齐。
- 若将来需要实时计数展示，可在阅读页读 Redis 而非数据库，但需评估额外的连接开销。
- IP 归属地解析（用于地区统计）本期不做，涉及引入 IP 库与更多个人信息处理，需单独评估。
